## §2 Shared contracts (verbatim)

**New method signature (binding):**

```python
def cost_by_request(self, request_id: str) -> float | None:
```

- Returns `float` = sum of `cost_usd` across all `llm_calls` rows with the given `request_id` where `cost_usd IS NOT NULL`.
- Returns `None` if no rows with non-null `cost_usd` exist for that `request_id` (including unknown `request_id`).
- Does NOT return `0.0` for missing rows — `None` semantics are required to distinguish "no cost data" from "cost was zero".
- Thread-safe: uses `self._lock` and `self._conn` consistent with all other methods.

**Rationale for `None` over `0.0`:** Ollama calls always have `cost_usd=NULL` in the store. `SUM(... WHERE cost_usd IS NOT NULL)` returns SQL `NULL` when no matching rows exist; mapping SQL `NULL` to Python `None` correctly distinguishes "no cost data" from "cost is exactly 0.0". `complete_structured` repair paths produce two rows for the same `request_id` — `SUM` handles multi-row aggregation correctly.

## §4 Subtask spec

**Files to touch:** `aria/observability/telemetry_store.py`

**Scope:** Add `cost_by_request` as an instance method of `TelemetryStore`. Place it after `cost_summary` (which is its nearest semantic neighbor).

**Implementation:**

```python
def cost_by_request(self, request_id: str) -> float | None:
    with self._lock:
        row = self._conn.execute(
            "SELECT SUM(cost_usd) FROM llm_calls WHERE request_id = ? AND cost_usd IS NOT NULL",
            (request_id,),
        ).fetchone()
    if row is None or row[0] is None:
        return None
    return float(row[0])
```

Note: `self._conn.execute(...).fetchone()` on a `SELECT SUM(...)` always returns exactly one row (never `None` for the row itself); `row[0]` is `None` when no matching rows exist. Both guard conditions are included for safety.

**Outputs:** Modified `aria/observability/telemetry_store.py` with the new method.

**Kill criteria:**
- **HALT** if `llm_calls` table schema differs from `(id, request_id, ..., cost_usd REAL, ...)` — do not adapt SQL to a different schema; report the actual schema found in `_init_schema`.

**Risks & mitigations:** None specific. The SQL is a simple single-table aggregate query. Thread safety is inherited from the `_lock` pattern used by all other methods.
